Каждый перенос требует проверки соответствующего поведения и сохранения данных.

## Проверка перед каждой сборкой или задачей

В локальном основном checkout и рабочей копии PR:

```powershell
git ls-remote automation refs/heads/develop
git fetch --no-write-fetch-head automation develop
git rev-parse automation/develop
git rev-list --left-right --count develop...automation/develop
git merge-base --is-ancestor automation/develop HEAD
git status --short --branch
```

На удалённом основном checkout те же команды выполняются с `origin`.

Начинать работу можно, когда живой опубликованный SHA совпадает с fetched-ref,
рабочий `develop` совпадает с ним, а текущий HEAD содержит эту основу.
У PR-ветки могут быть собственные новые коммиты поверх основы. При ошибке связи,
отсутствующем `develop`, расхождении или старой основе сборка останавливается.
Незакоммиченные изменения учитываются отдельно: один SHA не идентифицирует
сборку с изменёнными файлами. Для APK сохраняются SHA исходников, состояние WIP,
вариант сборки и SHA-256 самого артефакта.

Свежая дата локального коммита, название ветки и `versionName=1.0` не доказывают
свежесть основы. Android собирается на рабочем ПК; VPS используется как канал
доступа к удалённому ПК, сборка на нём не запускается.

## Один PR и последовательность замечаний

Общая ветка `codex/audit-fixes-20261014` создана из обновлённого локального
`develop`. Один черновик PR направлен в опубликованный `develop` репозитория
`coindmit-cmyk/InplaceX`. В него по порядку добавляются отдельные проверяемые
коммиты A01, A02 и далее по [ревизии](../reviews/2026-10-14-project-audit.md).

Следующий пункт — A02. Для него есть сохранённая правка Activity recreation
из `97d3c2f1`; переносить её нужно в актуальные исходники с проверкой реального
экранного ViewModel и обоих физических телефонов. Остальные локальные изменения
сохраняются до своего переноса. После каждого пункта фиксируются источники,
проверки, результат и фактические ограничения; новый пункт берётся после
завершения предыдущего. Решения о правилах продукта остаются отдельными входными
условиями соответствующих пунктов.

Используется script/Luna для реализации и диагностики, Sol — ограниченный резерв.
Задача, ID и накопленные квитанции сохраняются при продолжении. Существующая
локальная очередь остаётся источником полномочий; этот PR не меняет её схему,
состояние пауз, таймеры или аппаратные gates. Документ не запускает фоновые задачи.

## Возобновление конвейера и проверка свежести

Задача `INPX-AUDIT-A01-20261014` подготовлена для узкой автоматизированной проверки
свежести Git. Её первый CLI-процесс завершился ошибкой: установленный
`codex.cmd` ссылался на отсутствующий `codex.exe`. Модельного ответа и правок
в исходниках от этого запуска нет. Сохранены исходные task/input, fingerprint,
stderr, пустой поток событий, квитанция и суммарная статистика.

15 октября владелец явно разрешил продолжать работу без остановки на учёте.
Для текущей ревизии применён отдельный host-адаптер: приём новых вызовов не
блокируется неизвестным расходом, оригинальные квитанции и исходный ID сохраняются.
Первый неудачный вызов остаётся в журнале с `null`, числовых квот Luna нет.
Глобальная автоматизация, состояния очередей, границы исходников и резерв Sol
не изменяются. Рабочий CLI проверен через `--version`.

Luna реализовала `scripts/agent_control/develop_freshness.py` и девять интеграционных
проверок на локальных временных Git-репозиториях. Все девять проверок прошли.
Проверены сохранение WIP/index/stash/посторонних refs при fetch, старый и
разошедшийся develop, отсутствующая ветка, ошибочный remote и старая PR-основа.
Дополнительная host-проверка с повреждённым временным index также завершилась
правильным отказом. Новая проверка принимает свежие основные checkout и PR-копию,
а сохранённый старый результат `eb6e3ca3` отклоняет.

Перед следующей сборкой выполняется:

```powershell
python -B scripts/agent_control/develop_freshness.py --remote automation --fetch --json
```

На AiStudio имя canonical remote — `origin`. Ненулевой exit code запрещает
использование этой рабочей копии для сборки. CLI не переключает ветки, не делает
pull/reset/stash, не изменяет очередь и явно сообщает о WIP. До merge PR файл
доступен в его рабочей копии; основной develop по-прежнему совпадает с опубликованным.
